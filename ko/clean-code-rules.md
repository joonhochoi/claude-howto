# AI 코드 생성을 위한 클린 코드 규칙

이 규칙들은 유지보수 가능하고 전문가 수준의 코드를 생성하도록 코드 생성을 이끕니다.

## 의미 있는 이름
- 왜 존재하는지를 설명하는, 의도가 드러나는 이름을 사용하세요
- 잘못된 정보와 무의미한 구분(예: `data`, `info`, `manager`)을 피하세요
- 발음할 수 있고 검색 가능한 이름을 사용하세요
- 클래스 이름: 명사(예: `UserAccount`, `PaymentProcessor`)
- 메서드 이름: 동사(예: `calculateTotal`, `sendEmail`)
- 정신적 매핑과 인코딩(헝가리안 표기법, 접두사)을 피하세요

## 함수
- 함수는 작게 유지하세요(20줄 미만이 이상적)
- 한 가지만 수행하세요 - 단일 책임 원칙
- 함수당 하나의 추상화 수준
- 인자 수 제한: 0~2개가 이상적, 최대 3개, 플래그 인자는 피하세요
- 부수 효과 없음 - 함수는 이름이 말하는 대로 동작해야 합니다
- 명령(상태 변경)과 조회(정보 반환)를 분리하세요
- 오류 코드보다 예외를 선호하세요

## 주석
- 코드는 스스로 설명되어야 합니다 - 가능하면 주석을 피하세요
- 좋은 주석: 법적 정보, 경고, TODO, 공개 API 문서
- 나쁜 주석: 중복되거나 오해를 부르거나 나쁜 코드를 설명하는 주석
- 코드를 주석 처리하지 마세요 - 삭제하세요(버전 관리가 이력을 보존합니다)
- 주석이 필요하다면 코드를 리팩터링하는 방안을 먼저 고려하세요

## 서식
- 파일은 작고 초점 있게 유지하세요
- 수직 서식: 관련 개념은 가까이, 개념 사이는 빈 줄로 구분
- 수평 서식: 줄 길이 제한(80~120자)
- 일관된 들여쓰기와 팀 스타일을 사용하세요
- 관련 함수는 함께 묶으세요

## 객체와 자료 구조
- 객체: 데이터를 추상화 뒤에 숨기고, 메서드로 동작을 노출합니다
- 자료 구조: 데이터를 노출하고, 동작은 최소화합니다
- 디미터 법칙: 가까운 대상에게만 말하세요, `a.getB().getC().doSomething()`은 피하세요
- 게터/세터로 내부 구조를 무분별하게 노출하지 마세요

## 오류 처리
- 반환 코드나 오류 플래그 대신 예외를 사용하세요
- 실패할 수 있는 코드에서는 `try-catch-finally`를 먼저 작성하세요
- 예외 메시지에 맥락을 담으세요
- `null`을 반환하지 마세요 - 빈 컬렉션을 반환하거나 Optional/Maybe를 사용하세요
- `null`을 인자로 넘기지 마세요

## 클래스
- 작은 클래스: 줄 수가 아니라 책임으로 측정합니다
- 단일 책임 원칙: 변경 이유가 하나
- 높은 응집도: 많은 메서드가 클래스 변수를 사용
- 낮은 결합도: 클래스 간 의존 최소화
- 개방/폐쇄 원칙: 확장에는 열려 있고 수정에는 닫혀 있음

## 단위 테스트
- 빠름, 독립적, 반복 가능, 자체 검증, 적시(F.I.R.S.T.)
- 테스트당 하나의 단언(또는 하나의 개념)
- 테스트 코드 품질은 프로덕션 코드 품질과 같습니다
- 무엇을 테스트하는지 설명하는 읽기 쉬운 테스트 이름
- Arrange-Act-Assert 패턴

## 코드 품질 원칙
- **DRY (Don't Repeat Yourself)**: 중복 없음
- **YAGNI (You Aren't Gonna Need It)**: 가상의 미래를 위해 만들지 마세요
- **KISS (Keep It Simple)**: 불필요한 복잡함을 피하세요
- **보이 스카우트 규칙**: 발견했을 때보다 깨끗하게 코드를 남기세요

## 피해야 할 코드 스멜
- 긴 함수나 클래스
- 중복 코드
- 죽은 코드(사용하지 않는 변수, 함수, 매개변수)
- 기능 편애(다른 클래스에 더 관심이 많은 메서드)
- 부적절한 친밀감(클래스가 서로에 대해 너무 많이 아는 것)
- 긴 매개변수 목록
- 기본형 집착(작은 객체 대신 기본형을 남용)
- switch/case 문(다형성을 고려하세요)
- 임시 필드(때때로만 사용되는 클래스 변수)

## 동시성
- 동시성 코드는 다른 코드와 분리하세요
- 동기화/잠금 대상 데이터의 범위를 제한하세요
- 스레드 안전 컬렉션을 사용하세요
- 동기화 구역은 작게 유지하세요
- 실행 모델과 프리미티브를 파악하세요

## 시스템 설계
- 생성과 사용을 분리하세요(의존성 주입)
- 복잡한 객체 생성에는 팩토리, 빌더를 사용하세요
- 구현이 아니라 인터페이스에 맞춰 프로그래밍하세요
- 상속보다 합성을 선호하세요
- 디자인 패턴은 과시가 아니라 단순화될 때 적용하세요

## 리팩터링
- 큰 묶음이 아니라 지속적으로 리팩터링하세요
- 리팩터링 전후에 항상 통과하는 테스트를 확보하세요
- 작은 단계로: 한 번에 하나의 변경
- 자주 쓰는 리팩터링: 메서드 추출(Extract Method), 이름 변경(Rename), 이동(Move), 인라인(Inline)

## 문서화
- 자기 설명 코드 > 주석 > 외부 문서
- 공개 API에는 명확한 문서가 필요합니다
- 문서에 예제를 포함하세요
- 문서는 코드 가까이에 두세요(이상적으로는 코드 안에)

---

**핵심 철학**: 코드는 작성되는 횟수보다 10배 더 많이 읽힙니다. 영리함이 아니라 가독성과 유지보수성을 위해 최적화하세요.
